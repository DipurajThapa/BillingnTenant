# SUP-001 — Supabase identity and tenant boundary

**Status:** Implemented and verified against the named test project
**Scope:** Deferred integration activation; does not alter the Core Development Baseline

## Decision

Use Supabase Auth and a shared Postgres schema with strict RLS. Core code depends only on
`IdentityTenantPort`. The concrete adapter calls an allowlisted set of PostgREST RPC functions
through the fail-closed HTTP transport. Runtime probes use an authenticated actor JWT plus the
project publishable key; they must never use a secret/service-role key or database password.

The dedicated project `rsrztmgozovtjmbstlje` is the development/integration target. Although
Supabase labels its primary branch `PRODUCTION`, it is not an application production environment
and cannot support production verification claims.

## Security invariants

- `anon` has no table privileges.
- RLS is enabled and forced on every tenant table.
- Tenant membership is checked from `auth.uid()` through non-exposed, fixed-search-path helpers.
- New resources must belong to an active tenant and record the authenticated user as owner.
- Cross-tenant rows are invisible; unauthorized mutations affect no rows or return `42501`.
- Credentials are resolved from opaque handles at request time and never serialized.
- Operation names map only to `preflight_` RPC functions fixed by configuration.

## Verification evidence and claim boundary

The schema and RPC migrations are applied to the dedicated test project. Live database assertions
confirm RLS is enabled and forced, `anon` has no table or RPC access, own-tenant reads work,
cross-tenant reads/updates/deletes are hidden, revoked membership loses access, and fixtures roll
back. Two real Supabase Auth actors then exercised authenticated Data API probes for same-tenant
reads, reciprocal cross-tenant denial, create ownership, cross-tenant denial of the created resource,
and exact cleanup.

GitHub Actions run `34759024714`, attempt 4, job `103746440268`, completed successfully on
2026-09-13 and emitted `SUPABASE_LIVE_VERIFICATION_PASS`. Secrets were supplied only through
repository-secret handles and were not printed.

This authorizes a verification claim only for adapter `supabase-identity-tenant` against test project
alias `rsrztmgozovtjmbstlje`. It does not verify production readiness, a customer project, persistence
beyond the tested tenant boundary, Supabase uptime, or any other external integration.
